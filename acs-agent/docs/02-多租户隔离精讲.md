# 精讲：多租户隔离的三个维度（面试核心案例）

> 对应任务书第七节"多企业会话隔离"。这篇讲清三个正交维度、一个两层身份的坑，
> 以及为什么这套设计值得写进简历。

---

## 1. 三个维度各管一件事（正交，不混）

| 维度 | 一句话 | 类比 | 技术载体 |
|---|---|---|---|
| **工作区**（Workspace/Group） | 在哪儿干活 | 飞书的"群" | Miniclaw registered_groups，jid 如 `web:main` |
| **智能体档案**（Agent Profile） | AI 按什么规矩干活 | 值班员的岗位说明书 | 四段提示词 IDENTITY/SOUL/AGENTS/TOOLS |
| **身份绑定**（company_bindings） | 屏幕后面是谁 | 工牌刷卡 | chatJid → 企业名 或 internal 角色 |

**核心认知：前两者都不决定数据权限。** 换工作区、换档案，分诊台都是同一套说话
方式；能查谁的数据，只由绑定表决定。数据边界放在 **Python 工具层（资源层）**
强制（fail-closed），不放提示词——"确定性的安全规则放 Harness，不放模型自觉"。

## 2. 同一套系统、两种视图（实测矩阵）

| | 管理员（internal） | 企业客户（company，如示例企业乙） |
|---|---|---|
| AI/工具 | 分诊台，8 个工具全可用 | 同一分诊台；4 个内部工具被拒（forbidden） |
| 保养查询 | 任意设备 | 只能查自家设备，查他企 → `cross_company_denied` |
| 工单列表 | 任意企业 | 只返回自家（传入别家企业名被无视——按构造防枚举） |
| 建单 | 可代客建单 | 强制落到绑定企业（企业名写歪自动纠正并附 note） |
| 审批 | 可执行（必须人下结论） | 无权参与，只能查自己工单的审批进度 |

## 3. 两层身份的坑（实战教训）

Miniclaw 的会话身份有**两层键**：

```
工作区基础键:  web:c4d72e49-…              （registered_groups 在册）
会话复合键:    web:c4d72e49-…#agent:cc752ef9-…   （运行时 ctx.chatJid 真正用的）
```

- 解析带**基础键回退**：精确键查不到时，去掉 `#` 后缀再查一次——绑定一次工作区基础键，其中所有会话与定时任务自动继承；精确键（复合键）仍优先，可对单个会话做更细覆盖。
- 不用记键长什么样：未绑定调用会收到 `caller_unbound` 错误，**错误信息自带
  绑定命令**（`python -m acs.bind <复合键> <企业名|--internal>`），照抄即可。

## 4. 定时任务的一课（Scheduler × 隔离的交界）

- 定时任务只能挂**注册的基础工作区**；且只有管理员主工作区（Home）身份才能
  跨工作区指定目标（源码：`targetJid = hasCrossGroupAccess && args.target_group_jid
  ? args.target_group_jid : ctx.chatJid`）。
- 定时运行继承目标工作区的身份：挂在 `web:main` → internal → 保养扫描权限贯通。
- 模型两次失败都给出了**准确根因并诚实上报**（没编成功）——诚实原则在真实
  失败路径上的价值验证。

## 5. 简历/面试怎么说（一句版本）

"基于 Miniclaw 二开多租户售后智能体：调用者身份（会话 jid）与企业档案在工具层
强制绑定，默认拒绝、跨租户不可见；企业客户与内部角色共享同一智能体与工具面，
数据视图按身份自动切分——隔离策略不依赖提示词约束模型。"

面试追问预演：为什么放工具层不放提示词？（提示词可被绕过/漂移，资源层校验
是最后防线）为什么默认拒绝？（新会话未绑定时的爆炸半径最小）如何防枚举？
（列表工具对企业角色无视传入企业名，按构造消除越权面。）
